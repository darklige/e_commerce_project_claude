## 1. 项目愿景与核心理念

### 1.1 项目愿景
构建一个功能覆盖完整、用户体验流畅、多角色多端协同的电商平台，作为对京东（JD.com）业务生态的复刻性学习与工程实践。

### 1.2 核心开发理念

> **"做深做透，而非做多做浅"**

- **不追求功能数量**：不做覆盖式的功能堆叠。
- **追求业务深度**：任何决定实现的业务模块，都必须覆盖真实使用场景下的**正常流程、异常流程、边界流程、多方协作流程**。
- **可选模块可简化**：如支付环节，只需模拟支付逻辑；促销活动（打折/优惠券/满减）不打算深入的可完全不实现。
- **一旦实现，必须扎实**：例如订单退款，绝不能只有"用户申请 → 商家审核 → 退款完成"这条主路径，必须考虑：
  - 商家超时不响应怎么办？
  - 平台客服（管理员）何时/如何介入？
  - 用户寄回商品后商家拒收怎么办？
  - 部分退款、仅退款不退货、换货等衍生流程

### 1.3 业务思考的四个维度（每个功能都必须回答）

| 维度 | 关键问题 |
|---|---|
| **角色维度** | 用户端、商家端、管理员端各自拥有哪些操作？各自能看到哪些信息？ |
| **状态维度** | 该功能涉及哪些状态？状态之间如何流转？非法流转如何拦截？ |
| **异常维度** | 谁不响应、谁掉线、谁作恶？平台如何仲裁？ |
| **体验维度** | 页面加载 > 3s？点击反馈延迟？操作路径超过 3 步？弹窗打断用户？ |

### 5.3 权限技术实现

- 后端：基于装饰器/依赖注入的权限校验（`Depends(require_permission("order:refund:approve"))`）

## 6. 核心业务流程深度设计

以下以**订单退款**为例，展示"做深"的粒度，其他核心流程按此标准设计。

### 6.1 订单退款状态机

```
              [已下单]
                 │
              发货
                 ▼
              [已发货]
                 │
     ┌───────────┼───────────┐
     │           │           │
   用户签收   物流异常     用户拒收
     ▼           ▼           ▼
   [已完成]   [异常挂起]  [退货中]
     │
   申请售后
     ▼
   [退款审核中]────────┐
     │                 │ 商家超时未处理（72h）
   商家同意             │
     ▼                 ▼
   [待退货]         [平台介入中]
     │                 │
   用户寄回             │
     ▼                 │
   [待商家收货]         │
     │                 │
   商家收货确认      客服仲裁
     ▼                 ▼
   [退款中]───────→ [退款完成] / [退款拒绝（附理由）]
```

### 6.2 关键异常流程设计

| 场景 | 触发条件 | 平台响应机制 |
|---|---|---|
| 商家超时未审核退款 | 用户提交 72h 后无响应 | 自动升级至客服管理员，标记高优先级 |
| 商家拒收退货 | 商家点击"拒收" | 用户可在 7 天内申诉，客服强制介入 |
| 用户寄回后失联 | 商家收货但用户不再操作 | 15 天后自动确认收货并推进退款 |
| 用户恶意退款 | 系统检测短期高频退款 | 触发风控，需要客服人工审核 |
| 商品有质量争议 | 用户/商家双方均提供证据 | 客服上传仲裁结论、可要求平台鉴定 |

### 6.3 三方协作的关键设计点

1. **消息通知**：每次状态变化都要通知**利益相关方**（不多不少）
   - 用户申请退款 → 通知商家（+管理员看板不通知）
   - 商家超时 → 通知用户（"平台已介入"）+ 通知管理员待处理
2. **时间线可视化**：三方都能看到同一个订单的完整时间轴（但按权限展示不同细节）
3. **凭证系统**：申请、审核、仲裁的每一步都可上传图片/视频/文字凭证
4. **可撤销**：用户申请退款后，未审核前可以撤销；已审核后不可

### 6.4 用户体验优化的关键细节（"发现细节并优化"清单）

- ✅ 售后申请页：默认带上订单商品图和金额，无需用户重复填写
- ✅ 退货地址：商家同意退货时，自动填充商家退货地址（含快递面单二维码）
- ✅ 物流单号：支持输入后自动识别物流公司
- ✅ 售后进度：所有涉及方在自己的"我的订单"中都有醒目状态标记
- ✅ 退款到账：明确告知到账时间（"预计 X 个工作日"）和到账账户
- ✅ 售后历史：可查询所有历史售后记录，含双方所有沟通/凭证
- ✅ 快捷申诉入口：任何"待商家处理"的状态下，用户都能一键"催商家" + "申请平台介入"

## 9. 数据库设计原则

- 所有表包含 `id`、`created_at`、`updated_at`、`deleted_at`（软删）
- 金额字段用 `Numeric(12, 2)`，禁止用 `Float`
- 枚举字段用 PostgreSQL 原生 enum 或字符串 + 应用层 Enum
- 关联字段必须有外键约束和索引
- 状态变更类表要有配套的 `history` 表（如 `order_status_history`）
- 敏感字段（手机号、身份证）在应用层加密后入库
- 大字段（商品详情富文本）用 `JSONB` 或独立表

---

## 10. API 设计规范

- 遵循 RESTful，路径 `/api/v1/{scope}/{resource}`，如 `/api/v1/user/orders`
- 统一响应结构：
  ```json
  { "code": 0, "message": "ok", "data": {...} }
  ```
- 分页：`?page=1&size=20`，返回 `total`
- 错误码：4 位数字，模块化分段（1xxx 用户、2xxx 商品、3xxx 订单…）
- 所有请求/响应用 Pydantic Schema 严格校验
- 所有幂等操作（下单、支付、退款）必须支持 `Idempotency-Key`

## 11. 前端设计规范

- **配色**：主色借鉴京东红（`#E1251B`）但不完全复制，避免侵权
- **响应式**：Web 端支持 1280+ 桌面为主，移动端由 App 承担
- **无障碍**：核心操作按钮 aria-label、键盘可达
- **加载状态**：所有异步操作有 Skeleton / Loading / Error 三态
- **空状态**：所有列表页有友好的空状态设计
- **国际化预留**：文案通过 i18n key 引用，暂时只做中文
